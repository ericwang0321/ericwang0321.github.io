This guide is written for readers without a computer-architecture background. The intended reading order is:
how text enters the model → how the model computes → where the data is stored → why low precision saves HBM → why some GPUs or TPUs can run the model more easily than others.

Important: Until Kimi K3’s complete weights, layer-by-layer configuration, module dimensions and full deployment implementation are public, the capacity calculations in this guide must be treated as engineering estimates. “Mathematically runnable,” “runnable after adaptation,” “efficiently runnable,” and “production-ready” are four different levels.

Scope: The guide first places Kimi K3’s four core architectural components into one complete data path. It then estimates inference and training HBM, minimum accelerator counts, platform adaptation requirements and full-system deployment costs. Hardware specifications, public prices and product status are current to 21 July 2026. All prices are planning estimates rather than vendor quotations.

When the model runs, the chip is not literally “understanding text.” It is continuously moving and computing very large collections of numbers. Those numbers fall into several main categories:

Data What it is Where it is usually stored
Weight Model parameters learned during training and largely fixed during inference Storage, CPU memory and GPU/TPU HBM
Activation Intermediate results produced as the current input moves through each layer HBM, on-chip cache and registers
KV Cache / Latent Cache Historical attention information retained for later Tokens HBM
KDA State A compressed history state that KDA updates continuously HBM or cache closer to the compute units
Scale A shared scaling factor used by low-precision formats such as MXFP4 and MXFP8 Usually stored with the quantized data
Workspace / Buffer Temporary space used by Kernels, matrix multiplication, communication and scheduling HBM
Communication Buffer Send and receive buffers used by TP, EP and PP across accelerators HBM

This is why deciding whether an accelerator can run a model requires more than checking whether the Weight alone fits.

Part I — Fundamental Units: bit, Byte, GB, GiB and TB

1. What Are a bit and a Byte?

  • A bit (abbreviated b) is the smallest binary unit and can be either 0 or 1.
  • A Byte (abbreviated B) normally contains 8 bits.

The most important conversion is:

1 Byte = 8 bits

Therefore:

400 Gbit/s ÷ 8 = 50 GB/s

Capitalization matters:

  • Gb/s or Gbit/s means billions of bits per second.
  • GB/s means billions of Bytes per second.
  • Uppercase B and lowercase b differ by a factor of eight.

1.1 Decimal and Binary Units

Hardware vendors normally use decimal units:

1 KB = 1,000 Bytes
1 MB = 1,000,000 Bytes
1 GB = 1,000,000,000 Bytes
1 TB = 1,000,000,000,000 Bytes

Operating systems and some software also use binary units:

1 KiB = 1,024 Bytes
1 MiB = 1,024 KiB
1 GiB = 1,024 MiB
1 TiB = 1,024 GiB

Consequently, 192 GB and 192 GiB are not exactly the same capacity. Vendor-labelled capacity is adequate for rough estimates, but a deployment budget must use one consistent unit system.

2. How Do Parameters Translate into Weight Capacity?

Under an idealized calculation:

Weight capacity in Bytes
= number of parameters × bits per parameter ÷ 8

For a 2.8T-parameter model:

2.8T = 2.8 × 10^12 parameters

If each parameter uses BF16:

2.8 × 10^12 × 16 ÷ 8
= 5.6 × 10^12 Bytes
≈ 5.6 TB

With FP8:

2.8 × 10^12 × 8 ÷ 8
≈ 2.8 TB

With ideal FP4:

2.8 × 10^12 × 4 ÷ 8
≈ 1.4 TB

Kimi K3’s MXFP4 format also needs shared Scales. If 32 elements share one 8-bit Scale:

32 × 4 bits + 8 bits = 136 bits
136 ÷ 32 = 4.25 bits per parameter

The resulting simplified lower bound is:

2.8 × 10^12 × 4.25 ÷ 8
≈ 1.4875 × 10^12 Bytes
≈ 1.49 TB

This is only an ideal lower bound for Weight. It excludes:

  • layers or parameters not stored in MXFP4;
  • alignment, Padding and metadata;
  • Activation;
  • KV / Latent Cache;
  • KDA State;
  • AttnRes history buffers;
  • Kernel Workspace;
  • EP / TP communication buffers; and
  • memory consumed by the inference framework itself.

Therefore, “2.8T parameters require about 1.49TB in MXFP4” does not mean that 1.49TB of HBM is automatically enough to run the model.

Part II — What Are Weight, Activation and HBM?

3. What Is a Weight?

A Weight is one of the many numbers learned during model training. Most of the large matrices used in matrix multiplication consist of Weights.

A simplified linear layer is:

Output Y = Input X × Weight matrix W + Bias b

Here:

  • X is an Activation;
  • W is a Weight matrix; and
  • Y is a new Activation.

More parameters mean more Weight must be stored. Although an MoE model computes only a small subset of Experts for each Token, the Weight of every Expert must still be stored somewhere in the cluster.

3.1 A Weight Is Not a Stored Sentence of Knowledge

The model does not place the sentence “The capital of France is Paris” intact inside a particular Weight. Training distributes repeatedly observed relationships across many matrix elements. One Weight is only one number; large collections of Weights jointly determine how an input vector should be amplified, reduced, mixed or suppressed.

Consider a simplified example with three inputs:

z = x₁ × w₁ + x₂ × w₂ + x₃ × w₃ + b
  • x₁, x₂ and x₃ are Activations created by this input;
  • w₁, w₂ and w₃ are learned Weights;
  • b is a Bias, which is also a parameter; and
  • z is the new intermediate value passed to the next operation.

When the model is wrong during training, backpropagation estimates which Weights should change and by how much, after which the optimizer updates them. Once training is complete, ordinary inference repeatedly reads and reuses the same Weights rather than modifying them for each Token.

The distinction is therefore:

Weight: long-lived computation rules determined mainly by training
Input / Activation: request-specific data that changes on every run

3.2 Where Does Kimi K3 Contain Weights?

Weights do not exist only inside Experts. Major categories include:

  • Embedding Weight: looks up the starting vector associated with a Token ID;
  • KDA / Gated MLA Weight: projects inputs into queries, memory components, Gates or State-update components;
  • Router Weight: computes Expert scores from the current Token features;
  • Shared and Routed Expert Weight: performs large FFN / MLP feature transformations;
  • AttnRes Weight: helps the current layer decide which earlier Blocks should be read; and
  • LM Head Weight: converts the final vector into a score for every Token in the vocabulary.

This also explains why 2.8T × 16 ÷ 896 is not an exact active-parameter count. The 16/896 ratio describes only Routed Expert selection and excludes all of the always-needed Weight categories above.

3.3 Why Do Weights Dominate Capacity and Bandwidth?

One Token’s Activation is only a collection of vectors currently moving through the network. A 2.8T model, by contrast, must retain 2.8 trillion parameters. Even at an ideal 4 bits per Weight, the total is still about 1.4TB.

Before matrix multiplication begins, the required Weights also have to be read from HBM toward the compute units. If every generated Token requires large volumes of Expert Weight to be read, performance may be constrained by HBM bandwidth before it is constrained by peak FLOPS.

4. What Is an Activation?

After text is split into Tokens, each Token is first converted into a vector of numbers. That vector changes repeatedly as it moves through the layers. These changing intermediate values are Activations.

Activation is not fixed:

  • different inputs produce different Activations;
  • different Layers produce different Activations;
  • a larger Batch means more simultaneous Activations;
  • training retains more intermediate Activations for backpropagation; and
  • inference retains fewer, but still needs working memory and caches.

In short:

Weight is what the model has learned.
Activation is what the model is processing now.

4.1 Activation Versus Activation Function

The names are similar but the concepts are different:

  • An Activation is an intermediate number or tensor created while the model runs.
  • An Activation Function is a nonlinear function—such as SiLU, Sigmoid or Tanh—that transforms intermediate values.

Engineers often call Embedding outputs, Attention outputs, Q/K/V tensors, Router Scores, FFN intermediate vectors and Layer outputs “Activations.” They do not all need to have just passed through an Activation Function; in this context, Activation simply means input-dependent intermediate data produced during the current run.

4.2 Why Does a Neural Network Need Activation Functions?

A neural network repeatedly transforms its current representation into a representation that is more useful for the task. Early layers may identify local meaning, middle layers may combine syntax and references, and later layers may turn the resulting information into probabilities for the next Token.

If every layer were purely linear, stacking many layers would not create genuinely greater expressive power. Suppose two consecutive layers are linear:

h₁ = xW₁ + b₁
y  = h₁W₂ + b₂

Substituting the first equation into the second gives:

y = x(W₁W₂) + (b₁W₂ + b₂)

The result is still one larger linear transformation. Dozens of purely linear layers could be collapsed into one, leaving the model unable to form sufficiently complex curved boundaries, conditional choices and feature combinations.

An Activation Function inserts nonlinearity:

h = SiLU(xW₁)
y = hW₂

These two steps can no longer be collapsed into one matrix. Different inputs can activate, suppress or recombine different features, allowing the model to express rules such as: “if this context appears, strengthen one type of information; otherwise use a different transformation.”

In Kimi K3, nonlinear behavior is not confined to the conventional FFN:

  • Experts normally contain SiLU-, SwiGLU- or similar nonlinearities;
  • the Router produces different Expert scores from different Activations, sending different Tokens along different paths;
  • Gates in KDA and Gated MLA decide which information passes according to the current data; and
  • AttnRes changes how strongly the current layer reads earlier Blocks based on the current Activation.

4.3 How Does One Token’s Activation Change?

One Token’s journey can be viewed as repeatedly rewriting the same working representation:

Token ID
→ initial Activation returned by the Embedding lookup
→ Activation after incorporating historical information
→ Activation after Expert transformation
→ Activation after the Residual merge
→ input Activation for the next Layer
→ final Activation before the LM Head

Weight determines how each transformation is performed; Activation is the object being transformed this time. The same Weights produce entirely different Activations for different sentences. This input dependence is one fundamental reason why Activation is usually harder to compress to 4 bits than Weight.

4.4 Why Is the Activation HBM Budget Different in Training and Inference?

Inference only needs to continue forward to generate an answer, so many intermediate Activations can be released or overwritten after use. Training also performs backpropagation and must determine how each layer affected the Weight update. It therefore retains more intermediate Activations, or uses Activation Checkpointing to trade extra computation for lower memory.

For the same model:

  • Activation is often a major HBM item during training;
  • Weight usually dominates capacity for single-request inference; and
  • under high-concurrency, long-context inference, Activation, Cache, State and communication buffers can still grow rapidly.

5. What Is HBM, and What Must It Store?

HBM stands for High Bandwidth Memory. It is the fast memory placed next to a GPU, TPU or NPU compute package.

HBM has two core metrics:

  1. Capacity: how much data it can hold.
  2. Bandwidth: how much data it can read and write per second.

These must not be confused.

For example:

  • Enough capacity but insufficient bandwidth: the model fits, but Weight arrives too slowly.
  • High bandwidth but insufficient capacity: the chip is fast, but the model does not fit.
  • Enough capacity and bandwidth but slow interconnect: multiple accelerators spend their time waiting for communication.
  • Adequate hardware but a missing Kernel: the model’s mathematical structure cannot be mapped efficiently onto the chip.

5.2 Why Does a Longer Context Require More HBM?

Traditional Attention stores K and V for historical Tokens. KV Cache therefore grows approximately linearly with context length.

The main variables are:

Batch Size
× Context Length
× number of Layers
× number of K/V Heads
× dimension per Head
× Bytes per element

KDA uses a fixed or nearly fixed-size State, reducing cache growth for long contexts. Gated MLA compresses K/V and lowers the explicit Cache footprint. Neither means that memory requirements disappear entirely.

Part III — What Does “Precision” Mean?

6. Numerical Precision Is Not Answer Accuracy

FP16, BF16, FP8 and FP4 describe how many bits represent one number and how those bits are allocated among the sign, exponent and significand. They do not directly describe whether the model’s answer is correct.

A floating-point number can be approximated as scientific notation:

value ≈ sign × significant digits × 2^exponent
  • More exponent bits provide a wider dynamic range.
  • More significand bits distinguish nearby values more finely.
  • Fewer total bits reduce capacity and bandwidth pressure, but normally increase quantization error.

7. Common Numerical Formats

Format Bits per element General characteristics Common use
FP32 32 High precision and wide range; large footprint Reference computation and some accumulation
TF32 roughly a 19-bit effective encoding path Designed by NVIDIA for matrix computation Matrix multiplication in training
BF16 16 Exponent range close to FP32, shorter significand Large-model training and inference
FP16 16 More significand precision than BF16, narrower exponent range Training and inference
FP8 E4M3 8 Relatively better precision, narrower range Activation and Weight
FP8 E5M2 8 Wider range, lower precision Gradients and data with a wide dynamic range
INT8 8 Integer format requiring a Scale Inference quantization
FP4 / MXFP4 about 4 Very compact, with larger error Weight and selected matrix multiplication
INT4 4 4-bit integer requiring quantization parameters Weight-only inference

7.1 BF16 Versus FP16

Both use 16 bits, but allocate them differently:

  • FP16 has fewer exponent bits and more significand bits.
  • BF16 has more exponent bits and fewer significand bits.

As a result:

  • BF16 represents a wider dynamic range and is less prone to overflow.
  • FP16 distinguishes nearby values slightly more finely.
  • Large-model training often prefers BF16 because numerical stability matters more than the extra local resolution.

7.2 FP8 E4M3 Versus E5M2

  • E4M3 has four exponent bits and three significand bits.
  • E5M2 has five exponent bits and two significand bits.

An intuitive analogy is:

  • E4M3 is a shorter ruler with finer markings.
  • E5M2 is a longer ruler with coarser markings.

7.3 FP4 and INT4 Are Not the Same

Both may use four bits, but their encodings differ:

  • FP4 is floating point and includes an exponent concept.
  • INT4 is integer and normally uses a Scale and Zero Point.
  • INT4 support does not imply MXFP4 support.
  • Software being able to read a 4-bit Checkpoint does not imply that the chip can execute native 4-bit Tensor Core computation at full speed.

8. What Are MXFP4 and MXFP8?

MX means Microscaling. A small group of values shares one Scale.

8.1 Why Use a Shared Scale?

With only four bits, a value has very few representable levels. Giving each block of 32 values one shared Scale shifts that small group into a more useful numerical range:

real value ≈ low-precision value × shared Scale

Suppose a group of Weights is clustered near 0.001. Direct FP4 conversion might round many of them to the same value. Scaling the group before encoding it in FP4 can reduce that error.

8.2 Effective Average Footprint of MXFP4

32 elements × 4 bits = 128 bits
1 shared Scale = 8 bits
Total = 136 bits
Average = 4.25 bits per element

8.3 Effective Average Footprint of MXFP8

32 elements × 8 bits = 256 bits
1 shared Scale = 8 bits
Total = 264 bits
Average = 8.25 bits per element

8.4 Why Is MXFP4 Common for Weight While MXFP8 Is Common for Activation?

Weight is:

  • extremely numerous;
  • largely fixed during inference;
  • available for offline calibration; and
  • the most valuable target for aggressive compression.

Activation is:

  • generated dynamically from the input;
  • more variable in dynamic range;
  • capable of propagating error through every following layer; and
  • normally safer at a higher precision.

The basic allocation is therefore:

Weight: prioritize capacity and bandwidth savings → MXFP4
Activation: prioritize numerical stability → MXFP8
Accumulator: retain higher precision → FP16 / BF16 / FP32

This does not mean Weight is less important. Weight and Activation have different statistical behavior, usage patterns and failure modes.

Reason 1: Weight Is Fixed; Activation Changes with the Input

Weights are known before inference starts. Engineers can measure every Block’s range, select Scales, identify outliers and use Quantization-Aware Training (QAT) to help the model adapt to MXFP4 rounding error.

Activations are created at runtime. The same layer may produce very different distributions for ordinary conversation, source code, long digit strings or an extremely long context. A fixed 4-bit set of levels is more likely to encounter two problems:

  • small values collapse to zero or to the same level; or
  • large values exceed the representable range and are clipped.

MXFP8 has more representable values and a wider usable range, making it more tolerant of input-dependent variation.

Reason 2: Outliers in an Activation Block Affect Every Value Sharing Its Scale

MX formats share one Scale across a group. If an Activation Block suddenly contains one large outlier, the Scale must accommodate it. The smaller values are then squeezed into fewer encoding levels. Weight distributions are fixed and can be improved through training, grouping and offline calibration. Activation outliers depend on the current Token and are harder to anticipate.

Reason 3: Weight Is Enormous and Repeatedly Read

Compressing 2.8T Weights from 8 bits to roughly 4 bits can theoretically cut both Weight capacity and Weight-read traffic by almost half. That directly affects HBM requirements, accelerator count and the time each Token waits for Weight to arrive.

Activation also consumes bandwidth, but in low-Batch Decode for a large MoE, Expert Weight reads are often the more prominent cost. Applying the most aggressive compression to Weight first therefore tends to provide the largest system benefit.

Reason 4: Activation Error Immediately Enters Every Later Computation

One layer’s Activation is the next layer’s input. Excessive quantization error immediately affects Attention, Router, Gate, Residual and every later Layer. Weight quantization error also affects results, but it is fixed and can be jointly compensated by other parameters during QAT. Activation error varies with the input, Token and Layer, making it harder for the model to anticipate.

8.5 What Happens in One MXFP4 Weight × MXFP8 Activation Matrix Multiplication?

The operation can be divided into four steps:

1. Read packed MXFP4 Weight and its Scale from HBM.
2. Read the current layer’s MXFP8 Activation and its Scale.
3. Use the Scales to recover the numerical meaning and execute multiplication.
4. Accumulate many products in a higher precision such as BF16 or FP32.

One output of a matrix multiplication is normally the sum of many products:

yⱼ = x₁w₁ⱼ + x₂w₂ⱼ + ... + xₙwₙⱼ

Even when each multiplication uses low-precision inputs, accumulation needs more bits. Otherwise, repeatedly adding thousands of small products quickly magnifies rounding error or exceeds the low-precision format’s range.

W4A8 therefore normally means:

Weight input is mainly stored and multiplied at approximately 4 bits.
Activation input is mainly represented at approximately 8 bits.
The sum of products uses a higher-precision Accumulator.
The output is converted to MXFP8, BF16 or another format required next.

It does not mean that Norm, Softmax, Router, Gate, Residual addition and every intermediate tensor must use the same low precision. Numerically sensitive operations may remain in BF16 or FP32.

Kimi states that K3 begins adapting to MXFP4 Weight and MXFP8 Activation during the SFT stage. This form of QAT simulates deployment quantization and Scale behavior during training so that the model learns to operate in the presence of those errors. It improves viability, but does not automatically provide native chip instructions, efficient Kernels or a compatible Checkpoint Layout.

Using FP4 Weight and FP8 Activation also does not imply that the entire matrix multiplication remains at four or eight bits from beginning to end. Chips normally accumulate the result internally at a higher precision.

Part IV — Operators, Kernels and Inference Engines

9. What Is an Operator?

An Operator is a standard mathematical action in a neural-network computation graph.

Common Operators include:

  • Matrix Multiplication / GEMM;
  • Softmax;
  • LayerNorm / RMSNorm;
  • RoPE;
  • Top-K;
  • Gather / Scatter;
  • Convolution;
  • Scan;
  • All-Reduce;
  • All-to-All; and
  • Quantize / Dequantize.

For example:

Y = X × W

is a matrix-multiplication Operator.

The instruction:

Select the 16 Experts with the highest Router scores.

uses Top-K, sorting or selection Operators.

9.1 An Operator Is Not a Kernel

  • An Operator describes the mathematical or model-level action.
  • A Kernel is the concrete program that executes that action on one type of chip.

The same matrix-multiplication Operator may be executed by:

  • a CUDA / CUTLASS Kernel on an NVIDIA GPU;
  • a ROCm / HIP Kernel on an AMD GPU;
  • XLA-generated TPU instructions on a TPU; or
  • CANN / AscendC on an Ascend accelerator.

One analogy is:

Operator = the recipe instruction “sear”
Kernel = the exact heat and procedure written for one particular stove

9.2 Why Is an Operator Definition Not Enough?

A general framework may be able to assemble the correct result from many small Operators, yet run very slowly. High-performance deployment normally requires:

  • fusing multiple Operators;
  • avoiding intermediate writes back to HBM;
  • using the chip’s native low-precision matrix units;
  • arranging data in the expected memory Layout;
  • overlapping communication with computation; and
  • tuning for specific Shapes.

KDA, for example, may contain:

Linear projection
→ short convolution
→ Gate
→ State read
→ Delta update
→ State write

Launching one Kernel for each step and writing every intermediate result to HBM would be slow. The preferred implementation fuses these operations into one or a small number of Kernels.

10. What Is an Inference Engine?

An inference engine turns the complete model into a running service. It normally handles:

  • loading the Checkpoint;
  • distributing Weight across accelerators;
  • managing KV Cache and State;
  • scheduling Kernels;
  • dynamic batching;
  • Token Sampling;
  • Tensor Parallelism;
  • Expert Parallelism;
  • Pipeline Parallelism;
  • cross-accelerator communication; and
  • failure recovery and monitoring.

Common frameworks and engines include vLLM, SGLang, TensorRT-LLM, Megatron, JAX/XLA and MindIE. Support for a conventional Transformer does not automatically imply support for Kimi K3’s new structures.

Kimi K3 specifically requires validation of:

  • KDA State Update and long-sequence Scan;
  • Gated MLA’s compressed Cache and Gate;
  • AttnRes cross-layer history management;
  • Stable LatentMoE’s Latent projection;
  • 896-to-16 Expert routing;
  • MXFP4 Weight and MXFP8 Activation;
  • Grouped GEMM;
  • EP Dispatch / Combine; and
  • Quantile Balancing or other load-balancing logic.

Part V — Kimi K3’s Four Core Architectural Components

10.1 Put the Four Components Back into the Full Architecture

Before studying KDA, Gated MLA, AttnRes and Stable LatentMoE, it is important to understand that they are not four pieces of software that execute side by side. They operate on three different information flows:

  • information between the current Token and historical Tokens: handled by KDA or Gated MLA;
  • information carried by the current Token across different Layers: handled by AttnRes; and
  • feature transformation within the current Token: handled by Stable LatentMoE.

Placed back into one Token’s journey, the sequence is:

Token ID
  ↓ Embedding lookup
Initial vector
  ↓
┌──────────── Kimi K3 Block, repeated many times ────────────┐

  KDA or Gated MLA
  Let the current Token use information from prior Tokens
       ↓
  AttnRes
  Select which earlier Layer outputs remain useful
       ↓
  Stable LatentMoE
  Router selects 16/896 Routed Experts; Shared Expert runs
       ↓
  AttnRes
  Return the new Block result to the depth information flow

  ↓ Final Norm and LM Head
Scores for the next Token

Kimi’s official architecture shows a repeating unit of three KDA Blocks plus one Gated MLA Block. This indicates that KDA is the primary efficient path for compressed historical memory, with Gated MLA periodically providing more direct historical retrieval. It does not establish that Kimi has disclosed the model’s complete layer count; production deployment must still use the final Config.

Gated MLA Current Token Query and compressed historical Latent Cache Information retrieved from explicit historical positions A compressed State alone may not recall one old Token precisely Latent Cache, Attention Kernel and HBM bandwidth
AttnRes Current Layer representation and selected earlier Layer representations Depth-wise information weighted according to content A deep network need not rely only on one fixed residual path Activation history, cross-Pipeline-Stage communication and Depth Routing Kernel
Stable LatentMoE Current Token Hidden State Vector transformed by a small subset of Experts Use 896 Experts for capacity while computing only 16 per Token Expert Weight, Grouped GEMM, All-to-All and EP buffers

Two distinctions are especially important:

  1. An Attention Head is not an Expert. A Head retrieves information across Token history; an Expert applies a matrix transformation to the current Token’s features.
  2. The Latent in MLA is not the Latent in LatentMoE. MLA compresses Attention Key/Value information to reduce historical Cache. LatentMoE compresses the representation sent to routed Experts to reduce Expert Weight traffic and cross-accelerator communication.

10.2 Which Technology Is Triggered at Each Step?

Read prior context Update compressed State or read Latent Cache KDA / Gated MLA Dedicated State Update, Scan, compressed-Cache and Gate Kernels

Several additional names are often mixed together with “architecture,” but belong to different levels:

  • Per-Head Muon is an Optimizer used to update Weights during training, not a type of Attention.
  • SiTU is a nonlinear unit used in numerical and model design, not a multi-accelerator communication protocol.
  • QAT trains the model to tolerate low-precision error; it is not a new Layer.
  • WideEP spreads Experts across more accelerators; it does not change the fact that the model has 896 Experts.
  • DeepEP is a communication library for MoE Dispatch / Combine, while EPLB attempts to balance load across Ranks. Neither is a fifth core Kimi K3 architecture component.

11. KDA: Compressed Memory Along the Token Dimension

Traditional Full Attention stores K and V for every historical Token. KDA instead maintains a continuously updated State:

A new Token arrives
   ↓
Read the previous State
   ↓
Compute what the previous State predicts about the current information
   ↓
Compute the Delta between the new value and the old prediction
   ↓
Use a Gate to decide how much to retain and how much to update
   ↓
Write the new State

Hybrid architecture and KDA module from the Kimi Linear paper

Figure 2 | Figure 3 (p.6) of the Kimi Linear technical report. Source: arXiv:2510.26692. The figure explains the base KDA structure; Kimi K3’s official architecture additionally includes Gated MLA, Stable LatentMoE and Block AttnRes.

Read the paper figure in three parts:

  1. Begin with the vertical backbone on the left. The lower N× Blocks use KDA and the upper 1× Block uses MLA. KDA therefore does not remove every explicit Attention layer; it is mixed with a smaller number of MLA layers.
  2. Then examine the lower-right panel. The input enters from below and is projected through several Linear paths, some of which include short Conv operations. The symbols in the circles denote Gates or control quantities. They jointly feed Kimi Delta Attention, followed by Norm and Linear output.
  3. Finally inspect the upper-right panel. This expands the MoE: the Router selects Routed Experts while the Shared Expert always participates. KDA handles information mixing between Tokens; Experts transform features within one Token. They are complementary, not substitutes.

This figure documents the Kimi Linear mechanism. Its individual Shapes, per-layer counts and Gate positions must not be treated as the fully disclosed Kimi K3 configuration. Kimi K3’s official figure confirms the repeated 3×KDA plus 1×Gated MLA pattern, but the exact layer count and State Shape still depend on the final Config.

A simplified abstraction is:

New State
= retained part of the old State
+ the Delta information that needs correction

Advantages:

  • Long contexts do not require complete K/V storage for every old Token.
  • State size can remain fixed or nearly fixed during Decode.
  • HBM capacity and read pressure can be reduced.

Costs and limitations:

  • State is compressed memory, so details can be overwritten.
  • Prefill contains sequential recurrence dependencies.
  • Efficient execution requires Scan / Chunk algorithms and dedicated Kernels.
  • A conventional Attention Kernel cannot simply be substituted unchanged.

12. Gated MLA: More Precise Explicit Retrieval

MLA compresses K/V into a smaller Latent representation before storing it in Cache:

Full K/V
   ↓ compress
Latent Cache
   ↓ reconstruct or project when needed
Attention computation

MLA and MoE structure from the DeepSeek-V3 technical report

Figure 3 | Figure 2 (p.7) of the DeepSeek-V3 technical report. Source: arXiv:2412.19437. The figure is used only to explain the base MLA compression method; it is not a complete Kimi K3 architecture diagram.

When reading the figure, focus on the Transformer Block at left and the MLA area at lower right:

  1. The left panel shows Attention followed by FFN / MoE as two consecutive sublayers. MLA occupies the Attention position, while LatentMoE occupies the Expert/FFN position. MLA and LatentMoE are therefore not the same Latent technique.
  2. The lower-right panel separates Query, Key and Value into multiple projection paths. The hatched components labelled Cached During Inference are the compressed representations retained during inference. The key saving is that the model no longer stores complete K/V for every Head and every historical Token.
  3. RoPE-related components are handled separately because positional information cannot simply be discarded during compression. The current Query then participates in Attention with Key/Value reconstructed or projected from the Latent representation.

Kimi K3’s Gated MLA adds a Gate to MLA. Public information confirms that it is mixed with KDA, but the exact Gate location, formula and per-layer Cache Shape are not fully disclosed. We can therefore say that it preserves compressed explicit historical retrieval and uses a Gate to control information; the DeepSeek figure does not establish Kimi K3’s full implementation.

It remains a form of explicit Attention:

  • the current Token can still match explicit historical positions;
  • Cache still grows with Context length; but
  • the growth rate and per-Token footprint are lower.

KDA and Gated MLA can be viewed as:

Module Intuition Primary advantage
KDA A continuously updated summary Small Cache; well suited to long context
Gated MLA A compressed but searchable archive Easier precise recall of historical positions

Their combination balances efficiency with precise retrieval.

13. AttnRes: Information Selection Along the Layer Dimension

A conventional residual connection is approximately:

Current layer output = current layer transformation + previous layer input

As depth increases, information from prior layers is repeatedly accumulated. AttnRes instead lets the current Layer compute weights over selected earlier Layer representations:

Information read by the current layer
= Σ earlier Layer representation × dynamic weight

Standard, Full and Block AttnRes from the Attention Residuals paper

Figure 4 | Figure 1 (p.1) of the Attention Residuals technical report. Source: arXiv:2603.15031.

The figure presents three approaches from left to right:

  • (a) Standard Residuals: each sublayer adds its input directly to its output through a Shortcut. Old information accumulates, but the current layer cannot actively choose which earlier Layer it needs most.
  • (b) Full Attention Residuals: every Layer can read all earlier Layer outputs. The reddish-brown lines denote candidate history and α denotes content-dependent read weights.
  • (c) Block Attention Residuals: several Layers are grouped into a Block, and later Blocks read fewer representative historical states. This retains selection while reducing long-lived Activation storage and cross-Pipeline-Stage transfer.

The enlarged Q, K and V in the centre can be confusing. This Attention does not search historical Tokens; it selects among historical Layer or Block representations. It operates along model depth and can coexist with token-wise KDA or MLA.

Remember:

  • conventional Attention selects historical Tokens;
  • AttnRes selects historical Layers; and
  • the two operate along different dimensions.

13.1 Why Not Simply Pass the “Original Value”?

Each layer output is the model’s current representation, not a raw copy of the original input. A residual connection provides a shortcut for both information and gradients:

New representation = old representation + correction learned by this layer

Each layer learns how much to change instead of reconstructing the entire representation from zero. This makes deep networks easier to train and reduces the risk that early information is completely overwritten.

AttnRes goes one step further and lets the model decide:

Should this step read more from Layer 5, Layer 20, or the most recent Layer?

13.2 Block AttnRes

If every Layer remains available to every later Layer, the Activation history becomes large. Block AttnRes groups several Layers and retains fewer Block-level representations, reducing HBM use and cross-Pipeline-Stage communication.

14. Stable LatentMoE: Activating Only a Small Number of Experts

Kimi K3 stores a large number of Experts, but each Token activates only a small subset:

Current Token
   ↓ Router scores all Experts
Top-16
   ↓ Dispatch
Send the Token to the GPUs that own the selected Experts
   ↓ Grouped GEMM
Execute Expert matrix multiplications
   ↓ Combine
Merge outputs using the Routing Weights

Routed Experts and Shared Experts from the DeepSeekMoE paper

Figure 5 | Figure 2 (p.5) of the DeepSeekMoE paper. Source: arXiv:2401.06066. It illustrates the origin of Shared Experts and fine-grained Routed Experts; it does not imply that Kimi K3 uses the same Expert count or Top-K shown in the figure.

Read the figure from left to right:

  1. Conventional Top-2 routing selects two large Experts from one pool.
  2. The middle design divides large Experts into more fine-grained Experts and selects a correspondingly larger number, increasing the flexibility of Expert combinations.
  3. The right-hand design adds green Shared Experts. A Shared Expert is not conditionally enabled by the Router and handles more general capability; blue Routed Experts are selected per Token and focus on differentiated transformations.

Kimi K3’s official architecture similarly shows an always-on green Shared Expert path and Routed Experts selected by a Router. Stable LatentMoE additionally introduces Latent compression and stability-related routing design, so the DeepSeekMoE figure alone does not explain the full Kimi mechanism.

14.1 What Does 896 → 16 Mean?

  • There are 896 Routed Experts in total.
  • Each Token selects 16.
  • Different Tokens can select different Experts.
  • One Batch can collectively touch many or even all Experts.

You cannot compute:

2.8T × 16 ÷ 896

and treat the result as the exact active parameter count, because 2.8T also includes:

  • Embedding;
  • KDA / MLA;
  • Router;
  • Shared Expert;
  • AttnRes;
  • Norm;
  • LM Head; and
  • other non-Routed-Expert parameters.

14.2 Why Must Every Expert Still Be Stored?

Conditional computation reduces how much is computed this time; it does not reduce how much total model capacity must be stored.

MoE therefore has two different ledgers:

Capacity ledger: store all Expert Weight
Compute ledger: execute only Top-16 for each Token

14.3 What Does LatentMoE Change?

Standard MoE and LatentMoE from the LatentMoE paper

Figure 6 | Figure 1 (p.2) of the LatentMoE paper. Source: arXiv:2601.18089. The Latent down-projection and Latent up-projection in the right-hand diagram are the key to understanding the communication change.

The left diagram is a conventional MoE: the wide Hidden State is used for routing and sent through All-to-All; remote Experts receive and compute on that full-width representation.

The right diagram adds a shared Latent bottleneck around the routed Expert path. In the published base LatentMoE design, the Router still scores Experts from the full Hidden State. The payload sent to Routed Experts is then projected down before Dispatch:

Full Hidden State
  ├─ Router scores Experts in the full dimension
  ├─ Residual / Shared Expert retains the full dimension
  └─ Shared Latent down-projection
        ↓ narrower Latent payload
     All-to-All Dispatch
        ↓ Latent Expert computation
     All-to-All Combine
        ↓ Shared Latent up-projection
     Full model Hidden Dimension

This changes two major costs:

  • Less communication: GPUs exchange a narrower Latent payload rather than the complete Hidden State.
  • Less Expert Weight traffic: Routed Experts operate in a lower-dimensional space, allowing their expert-specific matrices to be narrower.

SE in the figure denotes the Shared Expert, which remains on an always-on full-width path. Kimi K3 has confirmed Stable LatentMoE and 896→16 routing, but the exact Stable modifications, Latent Dimension, Shared Expert count and precise active-parameter total cannot be inferred from this base paper figure.

Compression is not free or lossless. The down- and up-projections are trained end to end, the full residual stream remains available, and the latent width must stay above a task-dependent information floor. Compressing too aggressively can reduce quality. The published LatentMoE experiments found that roughly 4× compression preserved quality in the configurations tested, but that result does not establish Kimi K3’s unpublished compression ratio.

14.4 Why Does MoE Depend on the Network?

Once Experts are distributed across GPUs, a selected Expert may not reside on the current GPU. The Token must follow:

Dispatch All-to-All
→ remote Expert computation
→ Combine All-to-All

MoE therefore requires not only compute, but also an efficient accelerator interconnect.

Part VI — How Multiple Accelerators Run Kimi K3 Together

15. Three Common Forms of Parallelism

15.1 Tensor Parallelism (TP)

Tensor Parallelism splits one large matrix across several GPUs:

One large Weight matrix
→ split by rows or columns
→ several GPUs compute simultaneously
→ All-Reduce / All-Gather merges the results

Characteristics:

  • well suited to splitting Attention, shared projections and large Dense matrices;
  • normally involves several GPUs for every Token; and
  • requires a low-latency, high-bandwidth interconnect.

15.2 Expert Parallelism (EP)

Expert Parallelism places different Experts on different GPUs:

GPU 0: Experts 0–13
GPU 1: Experts 14–27
...

Characteristics:

  • particularly well suited to MoE;
  • Tokens move across GPUs according to Router decisions;
  • primarily depends on All-to-All; and
  • uneven Expert load leaves some GPUs busy while others are idle.

15.3 Pipeline Parallelism (PP)

Pipeline Parallelism places different Layers on different GPU groups:

GPU group A: Layers 1–20
GPU group B: Layers 21–40
GPU group C: Layers 41–60

Characteristics:

  • helps when the model is too deep to fit on one accelerator group;
  • moves Micro-Batches through the system like a pipeline;
  • can create a Pipeline Bubble; and
  • becomes harder when AttnRes needs representations from earlier Blocks, because those representations must be cached or transferred.

16. What Is WideEP?

WideEP extends Expert Parallelism across a larger number of accelerators.

Advantages:

  • each GPU stores fewer Experts;
  • aggregate HBM bandwidth increases;
  • more Expert Weight can be read in parallel; and
  • very large MoE models become easier to accommodate.

Costs:

  • a Token is more likely to be sent to a remote GPU;
  • the All-to-All domain becomes wider;
  • latency and congestion can increase sharply across Node boundaries; and
  • if the network is too slow, GPUs wait for data.

WideEP is therefore not automatically better when made wider. The useful point is where:

additional HBM-bandwidth benefit
>
additional cross-accelerator communication cost

MoE GroupGEMM from NVIDIA’s WideEP article

Figure 7 | Original GroupGEMM figure from NVIDIA’s developer article Scaling Large MoE Models with Wide Expert Parallelism.

The figure shows what happens after Tokens have already crossed the network and reached the destination GPU:

  1. Each row at left is a Token routed to this GPU; its colour identifies the Expert that should process it.
  2. Tokens for the same Expert are reordered and packed into a larger matrix. This avoids launching one tiny matrix multiplication for every Token.
  3. Several Experts’ FFN computations are passed to one fused Grouped GEMM Kernel. They are still separate matrix multiplications with different Weights, but scheduling them together improves compute-unit utilization and reduces Kernel launch and data movement overhead.

The complete WideEP path is therefore:

Router selects Experts
→ Dispatch / All-to-All sends Tokens to destination GPUs
→ Tokens are grouped by Expert
→ Grouped GEMM executes multiple local Experts
→ Combine / All-to-All returns results to the originating Rank

GroupGEMM solves “how to compute efficiently once the Tokens arrive.” It does not replace the preceding and following network communication. If NVLink or the inter-Node network cannot keep up as the EP domain widens, GPUs still wait during Dispatch and Combine.

Part VII — One Unified Scenario for Inference and Training Hardware

Separate the two workloads first. Request count, Context and KV Cache belong to inference. Training has no online requests or KV Cache; it must store Gradient, Optimizer State and the Activations needed for backpropagation. Both scenarios reserve 30% of HBM for items outside the main object, but that 30% contains different data.

17. Fix Two Scenarios Before Using Percentages

17.1 Inference Scenario: Weight Uses 70%; Everything Else Uses 30%

MXFP4 Weight and Scale ≈ 1.4875TB = 70% of total HBM
Total HBM ≈ 1.4875TB ÷ 70% = 2.125TB
Non-Weight space ≈ 2.125TB × 30% = 637.5GB

To turn 637.5GB into an understandable service workload, assume 128 Active Sequences at the same time, an average retained Context of 200K Tokens per request, and 16KB per active Token for the Gated MLA Cache.

128 requests × 200K Tokens = 25.6M active Tokens
25.6M × 16KB/Token ≈ 419GB KV/Latent Cache
637.5GB − 419GB ≈ 219GB

The remaining approximately 219GB must hold per-request KDA State, current Activation, Workspace, Expert communication buffers, Runtime, memory fragmentation and safety margin.

Because Kimi K3’s actual Bytes/Token and Bytes/Sequence have not been fully disclosed, this is a reproducible procurement baseline rather than an official minimum. If KDA State and Workspace exceed 219GB, more HBM is required.

17.2 Training Scenario: Parameter States Use 70%; Everything Else Uses 30%

Training cannot keep only one copy of Weight. The following teaching baseline uses standard Adam mixed-precision training. BF16 Weight, Gradient, FP32 Master Weight and two Adam States coexist, so their capacities are added.

Training data that coexists Bytes per parameter Purpose
BF16 Weight 2 Weight used by forward and backward computation
Gradient 2 Update direction calculated from the current Batch
FP32 Master Weight 4 High-precision copy used by the Optimizer
Adam first moment 4 Moving average of the Gradient
Adam second moment 4 Moving average of the squared Gradient
Total 16 Five different objects that exist at the same time 
2.8T parameters × 16 Bytes/parameter = 44.8TB of parameter state
44.8TB = 70% of total training HBM
Total training HBM ≈ 44.8TB ÷ 70% = 64TB
Activation, Workspace and communication buffers ≈ 64TB × 30% = 19.2TB

This 30% is not KV Cache. It covers training Activation, Operator Workspace, communication buffers, Runtime and safety margin. The 64TB estimate changes with the Optimizer, ZeRO/FSDP, Offload and the aggressiveness of Activation Checkpointing.

19. Must Training Use GB200 or GB300 NVL72?

Finding: No. Kimi has not disclosed Kimi K3’s actual training cluster and has not said that training requires GB200 or GB300. H100/H200 natively supports BF16/FP8 training; MI355X has published MXFP4 training results; and TPU7x explicitly targets large-model pretraining. GB200/GB300 NVL72 offers a 72-GPU high-bandwidth domain, mature training software and high HBM density. For that reason, the detailed economic model below is limited to those platforms and the next-generation NVL72 scenario.

21. Final Conclusions

  • Unified inference scenario: MXFP4 Weight is approximately 1.4875TB and occupies 70% of total HBM; total HBM is approximately 2.125TB.
  • The remaining 30%: approximately 637.5GB can represent 128 concurrent requests at an average 200K Context, with about 419GB of Cache and approximately 219GB left for KDA State and runtime overhead.
  • Capacity versus production: the inference capacity floor can be below 64 accelerators, but production deployment should still begin by evaluating Kimi’s recommended high-bandwidth domain of 64 or more accelerators.
  • Unified training scenario: 44.8TB of parameter state occupies 70%; Activation, Workspace and communication occupy 30%; total training HBM is approximately 64TB. Training has no online requests or KV Cache.
  • Training platform choice: GB200/GB300 are not the only hardware capable of training Kimi K3. They are simply the mature NVIDIA platforms most suitable for detailed Rack, time and cost modelling today.
  • A capacity floor is not a speed recommendation: four GB300 Racks can hold the 64TB scenario, but completing it in roughly 60 days still requires approximately 12 Racks under the stated assumptions.
