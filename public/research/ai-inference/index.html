推理原理入门：不懂这四件事，就看不懂这三家公司Inference 101: four things you must know before the companies make sense

"推理（Inference）"就是让训练好的模型干活——你发一个问题，它生成回答。听起来简单，但在几十亿次请求的规模下，怎么跑得快、跑得省，是一门深到能撑起百亿美元公司的工程学。 "Inference" simply means putting a trained model to work — you send a prompt, it generates an answer. Sounds trivial, but doing this fast and cheaply at billions-of-requests scale is engineering deep enough to support multi-billion-dollar companies.

2KV Cache：省下重复计算的"记忆"，但要吃掉海量显存The KV cache: memory that saves recomputation — and devours VRAM

Transformer 的注意力机制要求：生成每个新词时，都要"回看"前面所有词。如果每一步都重新计算前文，成本会随长度平方级爆炸。解法是把每个词算过的中间结果（Key 和 Value 两组向量）缓存起来——这就是 KV Cache。之后每一步只需算新词、查缓存。 Transformer attention requires each new token to "look back" at every token before it. Recomputing the past at every step would blow up quadratically with length. The fix: cache each token's intermediate results (its Key and Value vectors) — the KV cache. Every subsequent step only computes the new token and reads the cache.

代价是显存。GPU 显存里既要装模型权重，又要装每个并发请求的 KV Cache： The price is VRAM. GPU memory must hold both the model weights and a KV cache for every concurrent request:

对话越长、并发越多，KV Cache 越大——一个长上下文请求的缓存可达数 GB。缓存装不下 → 能同时服务的请求变少 → 单 GPU 产能下降。 Longer conversations and more concurrency mean a bigger cache — a single long-context request can consume gigabytes. When the cache doesn't fit, fewer requests run concurrently, and per-GPU output collapses.

为什么这是钱：KV Cache 直接决定一块 GPU 能同时服务多少人。谁能把 KV Cache 管理得更省（压缩、分页、复用），谁的单位成本就更低。后面你会看到，三家公司各有一套 KV Cache 的"抠门"办法。 Why this is money: the KV cache directly caps how many users one GPU can serve at once. Whoever manages it most frugally — compressing, paging, reusing — wins on unit cost. Each of the three companies has its own bag of KV-cache tricks, as you'll see.

小词典："负载"到底是什么意思？Mini-glossary: what exactly is a "workload"?

负载 = 一个系统当下要干的活儿的总量。一台 GPU 的负载，就是此刻压在它身上的请求——多少用户在同时等回答、每个请求有多长。"负载高"= 活儿多、机器忙不过来；"负载低"= 活儿少、机器闲着（但钱照烧——回忆那道除法题）。Load = the total amount of work a system has on its plate right now. A GPU's load is the requests currently pressing on it — how many users are waiting, and how long each request is. "High load" means too much work; "low load" means the machine idles (while the bill keeps running — recall the division problem).

三个常见变体：负载均衡器（load balancer）是把请求分给一堆 GPU 的"派单员"，别让有的累死、有的闲死——KV 感知路由就是个更聪明的派单员，派单时还记得你上次是哪个店员接待的。工作负载（workload）不光指量，还指活儿长什么样：编程助手是"短指令进、长代码出"，客服是"长历史进、短回复出"——同样一万个请求，形状不同，最优的优化方案完全不同（FireOptimizer、Engine Builder"量体裁衣"量的就是这个形状）。"把负载调度到哪"= 把活儿派到哪家云、哪个集群去干。一句话：负载 = 活儿；负载均衡 = 分活儿；工作负载画像 = 活儿的长相。Three common variants: a load balancer is the dispatcher handing requests out across a fleet of GPUs so none burns out while others nap — KV-aware routing is just a smarter dispatcher who remembers which clerk served you last time. A workload describes not just the volume but the shape of the work: a coding copilot is "short instruction in, long code out," support chat is "long history in, short reply out" — ten thousand requests of different shapes call for completely different optimizations (that shape is what FireOptimizer and Engine Builder "tailor" to). "Scheduling a workload" = deciding which cloud and cluster gets the job. In one line: load = the work; load balancing = dividing the work; a workload profile = the shape of the work.

小词典：FP16 / FP8 / FP4 具体怎么理解？Mini-glossary: what do FP16 / FP8 / FP4 actually mean?

FP = Floating Point（浮点数），计算机存"带小数的数"的格式；后面的数字是每个数占多少比特。模型的本质是一大堆数字（权重）：70B 模型 = 700 亿个数。每个数用 FP16 存占 2 字节，FP8 减半到 1 字节，FP4 再减半。落到实处：同一个 70B 模型，FP16 约 140 GB、FP8 约 70 GB、FP4 约 35 GB——模型还是那个模型，只是每个数记得"糙"了一点。FP = floating point — the computer's format for storing decimal numbers; the digit is how many bits each number takes. A model is fundamentally a pile of numbers (weights): a 70B model is 70 billion of them. Each number takes 2 bytes in FP16, 1 byte in FP8, half a byte in FP4. Concretely: the same 70B model weighs ~140 GB in FP16, ~70 GB in FP8, ~35 GB in FP4 — same model, each number just recorded more coarsely.

"糙"= 可表示的刻度变少。FP16 有约 65,536 种取值刻度，FP8 只剩 256 种，FP4 只剩 16 种。类比调色板：6 万色的照片 → 256 色的 GIF → 16 支马克笔。原来 0.4173 和 0.4188 是两个数，FP4 之下可能被记成同一个值。为什么变糙反而变快？①Decode 的瓶颈是搬权重（原理课第 1 点），体积减半 = 搬运时间减半；②新 GPU 有专吃低精度的硬件单元（H100 原生 FP8、Blackwell 原生 FP4），同样的晶体管每秒算的低精度乘加翻倍。附赠：KV Cache 也减半，同显存塞下翻倍并发。为什么敢压？神经网络的"知识"冗余地摊在几百亿个参数上，单个数记糙点整体行为几乎不变——像 RAW 照片压成 JPEG，文件小 10 倍肉眼看不出。为什么不能一刀切？少数数字很金贵：数值特别大的离群点、MoE 的路由器、注意力关键层，16 个刻度罩不住——所以手艺是混合精度 + 校准：敏感层保高精度，皮实层大胆压，压完跑基准验证智商没掉。"Coarser" = fewer representable notches. FP16 offers ~65,536 distinct values; FP8 just 256; FP4 only 16. Think color palettes: a 65k-color photo → a 256-color GIF → a box of 16 markers. Where 0.4173 and 0.4188 were once different numbers, FP4 may record them identically. Why does coarser mean faster? (1) Decode is bottlenecked on hauling weights (Inference 101 §1) — half the bytes, half the hauling time; (2) new GPUs have dedicated low-precision units (H100 native FP8, Blackwell native FP4) that crunch twice the multiply-adds per second from the same transistors. Bonus: the KV cache halves too, doubling concurrency per GPU. Why dare to squeeze? A network's "knowledge" is spread redundantly across billions of parameters, so coarsening any one barely moves the whole — like compressing RAW to JPEG: a tenth the size, invisible to the eye. Why not squeeze uniformly? A few numbers are precious: extreme outliers, MoE routers, critical attention layers — 16 notches can't hold them. Hence the craft: mixed precision plus calibration — keep sensitive layers high-precision, squeeze the sturdy ones hard, then benchmark to confirm no IQ was lost.

标准还是独家？分三层。格式是行业标准（FP8 规范由 NVIDIA/Arm/Intel 联合制定，FP4 属 OCP Microscaling 标准），硬件照标准造，人人同一把刻度尺；基础压缩算法（GPTQ、AWQ、SmoothQuant 等）是公开研究，谁都能做出"能用"的量化版本；独家的是手艺层——逐模型的配方（哪层碰不得）、高效跑混合精度的自研内核（FireAttention 的 FP8 实现闭源）、批量化的质量验证流水线。类比：JPEG 标准人人可查，但"这张照片压到什么参数看不出差别"的手感和产线是各家的。另注意措辞："无损量化"是营销话术——量化天然有损（刻度变少，信息必丢），实际承诺是"基准测试上测不出下降"，与 FlashAttention 那种逐位精确的真无损是两个级别的承诺。Standard or proprietary? Three layers. The formats are industry standards (the FP8 spec was jointly defined by NVIDIA/Arm/Intel; FP4 belongs to the OCP Microscaling family) — hardware implements them, and everyone shares the same ruler. The base algorithms (GPTQ, AWQ, SmoothQuant, etc.) are public research — anyone can produce a workable quantized model. The proprietary part is the craft layer: per-model recipes (which layers are untouchable), in-house kernels that run mixed precision fast (FireAttention's FP8 implementation is closed-source), and industrialized quality-validation pipelines. Analogy: the JPEG standard is public, but the eye for "how far this photo compresses before anyone notices" — and the production line behind it — belongs to each shop. One wording caution: "lossless quantization" is marketing — quantization is inherently lossy (fewer notches, information must go); the actual promise is "no measurable regression on benchmarks," a far weaker guarantee than FlashAttention's bit-for-bit exactness.

AFireAttention：从零重写的专有注意力内核FireAttention: a proprietary attention kernel, rewritten from scratch

开源世界的默认推理引擎是 vLLM（伯克利出品），性能已经不错。Fireworks 认为"不错"不够，从零重写了注意力计算的 GPU 内核，称为 FireAttention。官方宣称配合 FP8 量化，速度可达 vLLM 的约 4 倍（自家基准，需打折看待，但第三方测评常年把它列入延迟最低梯队）。V2 版本利用 H100 的 FP8 硬件单元再提约 2 倍吞吐，并且同一套内核适配 NVIDIA 和 AMD MI300 两家硬件——多一个供应商，就多一分议价权。 The open-source default is vLLM (from Berkeley), and it's decent. Fireworks decided decent wasn't the business, and rewrote the attention GPU kernel from scratch as FireAttention. The company claims ~4× vLLM with FP8 (its own benchmark — apply skepticism — though third-party tests consistently rank it in the lowest-latency tier). V2 exploits the H100's native FP8 units for roughly another 2× throughput, and the same kernel targets both NVIDIA and AMD MI300 — a second hardware supplier means bargaining power.

怎么理解"重写内核"：内核（kernel）是 GPU 上真正执行计算的小程序。同一道数学题，笨的写法让数据在"仓库"（显存）和"工作台"（计算核心）之间来回跑无数趟；聪明的写法把计算切成小块、在工作台旁边的"小抽屉"（高速缓存 SRAM）里一口气做完。数学结果一模一样，耗时天差地别。 What "rewriting a kernel" means: a kernel is the small program that actually executes math on the GPU. For the same equation, a naive kernel shuttles data endlessly between the warehouse (VRAM) and the workbench (compute cores); a smart one slices the work into tiles that finish entirely in the drawer next to the bench (on-chip SRAM). Identical math, wildly different time.

B"无损量化"：FP8/FP4 的艺术"Lossless" quantization: the art of FP8/FP4

回顾工具箱②：量化把模型数字从 16 位压到 8 位/4 位，数据量减半再减半——Decode 阶段瓶颈是搬数据，所以直接提速。但风险是模型变笨。Fireworks 的功夫在于不是一刀切地全压：逐层分析哪些部分对精度敏感（比如 MoE 模型的路由器、注意力的关键环节），敏感处保留高精度，不敏感处大胆压缩，再用基准测试验证质量没掉。这套"手艺"按模型逐个调校，是纯软件的 know-how。 Recall toolbox item ②: quantization halves (then halves again) the bits per number, from 16 down to 8 or 4 — and since decode is bottlenecked on data movement, that's a direct speedup. The risk is a dumber model. Fireworks' craft is refusing to squeeze uniformly: it profiles which layers are precision-sensitive (an MoE model's router, critical attention paths), keeps those in high precision, compresses aggressively elsewhere, then validates on benchmarks that quality held. This tuning is done per model — pure software know-how.

KV Cache 也被量化：把缓存里的 Key/Value 向量同样压到 FP8，同样的显存能装下近两倍的并发请求——回顾原理课第 2 点，这直接等于单 GPU 产能翻倍。 The KV cache gets quantized too: storing Key/Value vectors in FP8 fits nearly twice the concurrent requests in the same VRAM — and per Inference 101 §2, that translates directly into doubled per-GPU capacity.

CP/D 分离架构：让两种工作各回各家Disaggregated serving: send the two workloads to separate homes

传统做法是一块 GPU 既做 Prefill 又做 Decode。问题：一个用户发来超长文档触发大 Prefill 时，会把同 GPU 上所有人的逐字生成"卡住"（队头阻塞），表现为你的 AI 应用突然一顿一顿的。Fireworks 把整个服务栈按阶段拆开：Prefill 有专属 GPU 池，Decode 有专属 GPU 池，Prefill 算完把 KV Cache 移交给 Decode 池继续生成。两个池子按各自负载独立扩容，互不拖累。 The traditional setup runs prefill and decode on the same GPU. The failure mode: one user's giant document triggers a heavy prefill that stalls everyone else's token-by-token generation on that GPU (head-of-line blocking) — your AI app suddenly stutters. Fireworks split the stack by phase: a dedicated GPU pool for prefill, another for decode, with the KV cache handed off between them. Each pool scales to its own load, and neither drags the other down.

AFlashAttention：为什么"不改数学，只改搬运"能快 2–4 倍FlashAttention: same math, different data movement — and 2–4× faster

① 先补一课：注意力到底在算什么。模型生成每个新词时，要回答一个问题："前文里哪些词和我现在要写的最相关？"做法是给前文每个词打一个相关度分数，再按分数加权，把前文信息汇总成一份"摘要"。前文 1000 个词就打 1000 个分；而 Prefill 阶段每个词都要对每个词打分——1000 × 1000 = 100 万个分数，这就是那张"N×N 得分表"。文本长度翻倍，表变 4 倍大（平方级）。 ① First, the missing lesson: what attention actually computes. To write each new token, the model asks: "which earlier words matter most for what I'm about to say?" It scores every previous token for relevance, then blends the past into a weighted summary. A 1,000-token context means 1,000 scores per token — and during prefill, every token scores every other token: 1,000 × 1,000 = a million scores. That's the "N×N table." Double the text, quadruple the table.

② GPU 的"冰箱"和"灶台"。把 GPU 想象成厨房：HBM 显存是冰箱——容量大（几十 GB）但离灶台远、取用慢；SRAM 是灶台边的小料碟——伸手就到、极快，但只放得下一点点（几十 MB）。厨房规则：计算核心只能处理"手边"（SRAM）的数据，凡在冰箱里的必须先搬过来。而 GPU 的天性是算得飞快、搬得慢。 ② The GPU's fridge and countertop. Picture the GPU as a kitchen: HBM is the fridge — huge (tens of GB) but far from the stove and slow to reach; SRAM is the little prep bowl beside the burner — instant, but it holds almost nothing (tens of MB). House rule: compute cores can only work on what's within arm's reach (SRAM); anything in the fridge must be carried over first. And a GPU's nature is to compute far faster than it can carry.

③ 标准算法慢在哪。注意力要三步：算出整张得分表 → 每行归一化（softmax，把分数变成总和为 1 的权重）→ 加权求和。致命处：那张 100 万格的表料碟根本放不下，于是每一步之间都只能整张搬进冰箱、再整张搬出来——同一张大表来回搬三四趟。真正的计算只占零头，时间几乎全耗在搬运上。 ③ Why the standard algorithm crawls. Attention takes three steps: build the score table → normalize each row (softmax turns scores into weights summing to 1) → take the weighted sum. The killer: the million-cell table can't possibly fit in the prep bowl, so between every step it gets hauled to the fridge and back — three or four full round trips for the same table. The arithmetic is a rounding error; nearly all the time goes to carrying.

④ FlashAttention 的解法。关键发现：归一化和加权求和并不需要等整张表算完。把前文切成小块（小到能进料碟），算一块的分数 → 立刻归一化 → 立刻累加进一个"进行中的汇总" → 把这块分数直接扔掉 → 算下一块。其中有个数学技巧（online softmax）：每来一块新分数，就回头按比例修正之前的累积值，所以分块算出的结果与一次性算完精确一致，不是近似。整张大表从头到尾没被完整写出来过——冰箱只开两次（取原料、存成品），中间所有草稿都在料碟上完成、用完即弃。搬运量骤减：速度提升 2–4 倍，显存占用从 N² 降到 N。 ④ FlashAttention's move. The key realization: normalizing and summing don't require the finished table. Chop the context into chunks small enough for the prep bowl: score one chunk → normalize immediately → fold it into a running summary → toss the scores → next chunk. A mathematical trick (online softmax) retro-corrects the running totals as each new chunk arrives, so the chunked result is bit-for-bit identical to computing everything at once — not an approximation. The million-cell table never fully exists; the fridge opens exactly twice (fetch ingredients, store the finished dish), and every scrap of scratch work lives and dies in the prep bowl. Carrying collapses: 2–4× faster, memory from N² down to N.

一句话总结"不改数学，只改搬运"：同样的公式、同样的硬件，纯靠重新安排计算顺序就快了好几倍。推理公司赚的"优化差价"，本质就是无数个这种量级的安排技巧叠出来的。 The takeaway behind "same math, different logistics": identical formula, identical hardware — several times faster purely by reordering the work. The "optimization spread" these companies monetize is exactly this kind of trick, stacked dozens deep.
再深一层：FlashAttention-3 与 FlashDecodingOne level deeper: FlashAttention-3 and FlashDecoding

FA-3（2024），一句话：让"搬"和"炒"同时进行——一个人去冰箱搬下一块食材时，另一个人正在炒上一块，谁也不等谁。具体做法是利用 H100 的专用搬运引擎（TMA）异步搬数据、计算单元同时处理上一片，并交错执行矩阵乘法与 softmax，还支持 FP8。相比 FA-2 再快 1.5–2 倍。这类优化必须贴着每代新硬件重写——这正是养一支顶级内核团队的意义。FA-3 (2024), in one line: carry and cook at the same time — one person fetches the next ingredient from the fridge while another is already cooking the last one, and nobody waits. It chops the long KV cache into segments, lets every core compute attention over its own segment in parallel, then merges the partials. The box itself is worthless; what standardization unlocks is the point — anything in the box can enter Baseten's fully automated pipeline downstream.

第 2 步：量体裁衣（Engine Builder）。通用推理引擎像均码衣服：谁都能穿，谁穿都不合身。Baseten 的 TensorRT-LLM Engine Builder 做的是"高级定制"：拿到你的模型后，按三个尺寸——模型结构、GPU 型号、你的典型输入输出长度——提前把整条计算流程"焊死"成一台专用机器。核心动作叫算子融合：把几十个小计算步骤合并成几个大步骤，中间结果不再反复搬进搬出显存（和 FlashAttention"减少搬运"是同一个思想，只是作用于整个模型）。代价：换模型要重新定制（自动完成，几十分钟到几小时）；回报：生产实测约 2 倍吞吐——同样的硬件账单，服务翻倍的请求。 Step 2: tailor it (Engine Builder). A general-purpose engine is one-size-fits-all clothing: everyone can wear it, no one looks good. The core move is operator fusion: merging dozens of small steps into a few big ones so intermediate results stop shuttling in and out of memory (the same "move less data" idea as FlashAttention, applied model-wide). Cost: a new model means re-tailoring (automatic, tens of minutes to hours). Payoff: about 2× measured production throughput — double the requests on the same hardware bill.

B开店之后：一块 GPU 怎么又快又稳地同时服务很多人Running the shop: serving many people on one GPU, fast and without falling over

拼车，但要拼得聪明。一块 GPU 太贵，不能一人独占，所以要把很多用户的请求"拼"在一起算（工具箱③）。老式拼法像旅行团：凑满一车才发车，还得等最慢的游客逛完，全车人才能走——你问了句"你好"，却要陪别人生成三千字长文。连续批处理改成公交车：每生成一个词的间隙就是一"站"，答完的请求立刻下车，新请求立刻上车，GPU 时刻满载，谁也不陪跑。 Carpool — but carpool smart. Baseten 的功夫在"装车的艺术"。决定一车装多少时，它数的不是人头而是行李——显存是被 token 数吃掉的，不是被请求条数吃掉的（回忆原理课第 2 点：每个请求的 KV Cache 大小取决于文本长度）。装太松，GPU 白白空转；装太猛，显存当场爆掉（OOM），整个服务崩溃。贴着显存上限装车而永不超载，就是它调度层最值钱的手艺。 Baseten's craft is the art of packing the bus. When deciding how much fits, it counts luggage, not heads — VRAM is consumed by tokens, not by request count (recall Inference 101 §2: each request's KV cache scales with its text length). Pack too loose and the GPU idles; pack too greedy and memory blows (OOM) — the whole service crashes. Loading right up against the memory ceiling without ever tipping over is the scheduling layer's most valuable skill.

老顾客要找回老店员（KV 感知路由）。回忆原理课：你和模型对话的"记忆"（KV Cache）存放在某一块具体的 GPU 上。普通负载均衡器把你的第二句话随机扔给任何一台 GPU——那台机器没有你的记忆，只好把你们之前聊的全部内容从头重算一遍，你就干等。Baseten 的路由器记得你的对话存在哪台 GPU 上，把后续请求精确送回那一台——记忆还热着，接着聊就行，首字延迟骤降。多轮对话和 Agent（一次任务几十轮往返）场景下，这一招的差距是数量级的。 Regulars should get their usual clerk (KV-aware routing). Recall Inference 101: the "memory" of your conversation (its KV cache) lives on one specific GPU. A naive load balancer tosses your second message to any random machine — which has no memory of you, so it recomputes your entire history from scratch while you wait. Baseten's router remembers which GPU holds your conversation and sends every follow-up straight back to it — the memory is still warm, the chat just continues, and time-to-first-token plummets. For long conversations and agents (dozens of round trips per task), the gap is an order of magnitude.

Traffic doubles; the obvious response is "spin up another GPU." But "spinning up" isn't quick: first download tens of GB of model weights (like stocking a new branch before opening), load them into VRAM, initialize the engine — naively 10+ minutes, by which point the rush has passed or the service has already collapsed. 第二关：别把店开在一个房东手里（多云调度）。Baseten 自己基本不囤 GPU。它在 18 家云、87 个集群之上运营一个"总调度台"：哪家云此刻有空闲 GPU、哪家便宜、哪家离用户近，活就派到哪；某家云的某个区域挂了，流量自动切到别家，用户毫无感觉。它还能把整套系统开进客户自己的云账户里——数据一步不出客户家门（医疗、金融客户的硬要求），只有突发流量才溢出到 Baseten 的公共池。这个调度台没有捷径：每家云的 GPU 什么时候有货、网络什么脾气、故障长什么样，都是一个坑一个坑踩出来的——这正是它最难被复制的资产。 Gate two: never rent your whole shop from one landlord (multi-cloud orchestration).
